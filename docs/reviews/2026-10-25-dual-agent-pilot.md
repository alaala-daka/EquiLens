# 主审与独立复核对照实验

范围：Demo 开发期的 Node.js CLI 实验。网页默认流程未接入复核角色，不改变成果或人工复核状态。
契约：[架构实验入口](../../spec/00-overview.md#主审与复核的受控对照实验)。

## 实现与边界

- 同一次主审原件追加独立复核。复核工具只提交「保留 / 需人工核对」，按原规则和来源枚举约束，逐字校验引文。
- 原始结果保持不可变；复核不能改写合同、删除待核实项或赋予人工通过状态。
- 每轮两个角色共用 25 次请求预算、600 秒总时限；保留请求预留、原始响应、主审、复核和指标，失败不覆盖前次输出。
- 复核按最多 3 条分批，传入完整解析范围、全部主审结论及本批规则/来源。只开放提交意见工具。
- 可显式指定复核 low 推理强度，主审和网页配置不变。供应商不支持时明确失败。
- 独立复核说明文本不保证正确，不当作法律结论或已确认的修改指令。

## 真实模型运行

2026-10-25，读取获授权的本机 `.env.local`，使用 `api.deepseek.com` 的 `deepseek-flash`。
只发送仓库合成夹具，没有发送先前那份 69 段合同。全部使用 debug 模式，规则与来源仍待核对。
自然输入为 `fixtures/sample-contract.txt`，18 段、19 条必检规则。
两轮自然对照及两组预设检查合计 42 次真实请求、431,680 token，包含首轮未完成的复核，未隐去失败开销。

### 首轮：供应商默认推理

主审 14 次、49.369 秒，175,560 token；主审成功，没有待核实或拒绝项。
追加复核后合计 19 次、122.386 秒、218,552 token，但只完成 5/19 条，14 条未核对，状态为 partial。

失败证据：复核第 16 次实际请求 `finish_reason=length`，8,192 个生成 token 全部为 reasoning token，正文为空；
有界修正后的输出又把规则 ID `MEASURE-001` 放入来源 ID 列表，被校验拒绝。
模型修正来源后逐条提交，但本批有界步骤耗尽，未提交完 3 条，程序停止并保留主审及 5 条意见。
不能把该轮记为成功，或将未核对项目计为通过。

输出：`.superpowers/audit-comparison/comparison-831191e2-2ae8-4c9b-88ab-8c0a4244af5d/`。

### 修正后：来源枚举＋显式 low

将规则和来源 ID 约束加入模型工具 schema；复核角色使用其专属截断修正说明，避免引用主审提交工具名。
仅对复核显式设置 low。参数依据为 [DeepSeek 官方思考模式文档](https://api-docs.deepseek.com/guides/thinking_mode/)：
支持 `reasoning_effort=low`，供应商默认启用思考并使用 high。实际请求已核对传入 low。

这是新的独立运行，重新进行主审；它与首轮的主审自然输出不同，不能把跨轮差异归因于单一参数。
以下只比较本轮同一次主审原件与追加复核的开销，耗时是模型阶段，不含导入、解析或网页操作。

| 指标 | 仅主审 | 同一主审＋复核 |
| --- | --- | --- |
| 请求数 | 12 | 19 |
| 耗时 | 51.275 秒 | 142.866 秒 |
| 已知 token | 145,581 | 201,951 |
| 复核覆盖 | — | 19/19 |
| 新增机器核对意见 | — | 13 条 |

复核增加 7 次请求、约 91.6 秒、56,370 token（约 +38.7%）。7 次复核响应均正常结束，无来源拒绝或漏答。
主审本身有 1 次引文输出被拒绝后纠正，以及 1 条 `MEASURE-003` 待核实，最终状态为 partial；
追加复核没有删除该待核实项、修改主审结果或将其提升为 success。复核自身的完成状态为 completed。

输出：`.superpowers/audit-comparison/comparison-71c44483-4002-4a91-b2ce-74cc0c3b7c7f/`，
包含 `primary.json/md`、`audit.json`、`comparison.json/md`、manifest 和每次实际请求/响应。

## 预设文本忠实度正反例

预期在运行前保存在 `fixtures/audit-challenges.json`，不属于自然主审结果，不计入自然改进数据。

| 合成情况 | 预期 | 默认推理实测 | low 实测 |
| --- | --- | --- | --- |
| 原文依赖上游付款，机器却称不受上游影响 | 需人工核对 | 符合 | 符合 |
| 忠实描述上游付款前提及其不确定性 | 保留 | 符合 | 未符合，提出通则法条是否支持结论的疑点 |

默认推理两例各 1 次，共 6,000 token；low 两例各 1 次，共 5,177 token。
low 的正常对照没有满足预设，不更改预期。它提示可能存在过度核对；该法源疑点是否属于误报仍需领域判断。
不能把 13 条核对意见当成 13 处已确认错误，也不能据两例计算法律准确率。

输出分别为 `.superpowers/audit-comparison/comparison-81ebac4a-db60-4301-a2c8-864c905beef2/`、
`.superpowers/audit-comparison/comparison-f50a7715-bede-4800-b9e4-7e2498b2cfb6/`。

## 观察与采用结论

原文对应检查有价值。例如首轮 PAY-001 主审称没有验收前提，而其引文已明确“工程竣工验收合格后”；
第二轮 PAY-002 主审称无起算点，但原文存在收到结算资料这一事件。复核能提出此类文字对应问题。
机器还提出来源支持程度、跨规则重复等意见，其正确性及法律适用未独立评估。

本轮结论是保留可运行的旁路复核实验，暂不替换默认网页流程。
复核带来明确的额外耗时和用量，也有过度提示风险；仅凭当前样本不能证明漏检、误报或总体业务质量改善。
它不替代产品 §12.1 的独立标注、业务评测集或发布门槛。

## 本地工程验证与复现

Windows / Node.js 24.16.0 / pnpm 11.6.0。
`pnpm check`、`pnpm build`、`git diff --check` 通过；`pnpm test` 为 210 项，209 通过、1 项原有 Linux fsync 检查跳过。
新增 6 项复核测试，覆盖主审不可变、来源/引文、重复与漏答、累计预算、取消、权限预留失败、
部分失败、low 参数及 schema 枚举实际请求、未知工具不能扩大权限。
没有修改依赖，没有新增服务，没有推送或发布。

```sh
pnpm review:contract:compare --contract tools/contract-review/fixtures/sample-contract.txt --debug --audit-effort low
pnpm review:contract:compare --challenge --debug --audit-effort low
```

两条命令都读取 `.env.local` 并产生真实模型调用。每次保存独立目录，前次输出保留。
新运行可能出现不同输出，不能保证复现相同结论或时间；预设检查未匹配时退出码为 2，并保留实际意见。
