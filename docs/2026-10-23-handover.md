## 3. 破坏性契约变更（务必同步）

### ① 提交审查的上下文

```diff
- context: { role: "专业分包人", projectType: "房建机电安装专业分包", region: "江苏" }
+ context: { scene: "mep-sub-2026", region: "江苏" }
```

立场与项目名称由场景表给出，客户端不再决定。未同步会返回 422。
涉及：`src/lib/contract-reviews/types.ts`（`SubmitContext`）、`tasks/service.ts`（`submitReviewSchema`）、`components/contract-review-panel.tsx`。

### ② 规则文件的适用条件

```diff
- "appliesTo": { "projectType": "房建机电安装专业分包", "role": "专业分包人" }
+ "appliesTo": { "scene": "mep-sub-2026", "role": "专业分包人" }
```

`projectType` 不再参与判定；写未登记的场景标识会让**规则包直接加载失败**（有意为之，避免静默失效）。

### ③ 任务快照里的 context

数据库表结构未变，但 `equilens_review_tasks.input` 中的 `context` 结构已变。旧任务缺 `scene`，被恢复/重试时会全部落到"条件未知 → 待核实"。

## 4. 怎么跑

```bash
pnpm dev                      # 必须用这个：会先生成 DOCX 校验器
pnpm check                    # eslint + typecheck
pnpm test                     # 全部单元测试
pnpm ai:smoke                 # 模型连通性（发一条固定测试消息）
```

**坑一**：直接用 `next dev` 启动，`scripts/generated/docx-validator.mjs` 不会被生成，上传一律报"文档校验失败"。手动修：`node scripts/build-docx-validator.mjs`。

**坑二**：`.env.local` 与规则文件都在启动时读取，改完要重启 dev server。

**坑三**：Node 要求 `>=24 <27`（见 `package.json` 与 `.node-version`）。

## 5. 已知限制（交付前必须处理）

| 限制 | 影响 | 建议 |
| --- | --- | --- |
| 只有 6/19 条规则可发布 | 正式模式只跑 6 项检查，其余 13 项不出现在报告里 | 领域同学核对 `sources/internal.json` 的 5 条来源；它们当前带 `illustrative: true`（合成示例），解析器禁止发布 |
| 规则包为"临时测试发布" | `reviewer` 字段写的是"临时测试发布（未完成领域核对）" | 核对完成后换成真实核对人与日期；`tests/review.test.ts` 会自动恢复严格断言 |
| 地域字段无规则使用 | 用户必填但填什么都不影响结果 | 要么去掉输入，要么把地方性规定接进规则 |
| 调用上限 25 次 | 超长合同可能耗尽次数，降级为 partial | 需要更大的合同必须先扩上限或改分批策略 |
| 正式模式依赖已发布规则 | 规则未发布时提交直接报错 | 与上一行同源，属于有意设计 |

## 6. 待优化事项

按项目决定，本次提交接受"规则临时发布"状态用于线上联调，**不作为对外承诺**；下列事项按优先级记录。

| 事项 | 现状 | 建议 |
