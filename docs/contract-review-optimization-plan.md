# 合同审查模块优化计划

> 状态：提案，未经评审。本文不是已接受的契约，实现前需按 `AGENTS.md` 的要求先更新
> `spec/00-overview.md` 中合同审查相关的预算与提示构造条款。
> 日期：2026-10-22。基线分支 `feat/contract-review-handoff`，提交 `93565d1`。

## 1. 现状

当前实现是一条硬编码的固定流程：解析文档为带编号段落 → 按关键词标出候选段落 →
七条规则一批 → 把**整篇合同**连同规则和法条送模型 → 逐条校验引文与来源 → 计算六类覆盖
→ 返回 `success` / `partial` / `failed`。

模型在其中只做一件事：依据规则判断条款是否合规，并抄出原文依据。范围由规则包和代码决定。

这条流程有三个具体缺陷：

| 缺陷 | 表现 | 来源 |
| --- | --- | --- |
| 长合同跑不了 | 每批都携带全篇，提示超过 24,000 字符时该批直接失败 | `tools/contract-review/src/review.ts:137` |
| 四个业务不复用 | 管道与"合同六类"耦合，投标核验、款项核对、催款函接不进来 | `review.ts` / `validate.ts` 中的合同专用字段 |
| 漏查看不见 | 非必检规则靠关键词命中才进批次，未命中时既不检查也不记录 | `match.ts:48`、`buildCoverage` |

## 2. 优化方向

与现状逐项对照：

| 环节 | 现状 | 优化后 | 解决什么 |
| --- | --- | --- | --- |
| 文档结构 | 全程持有段落数组，无结构划分 | 按"第X条"切成块，并生成全文目录 | 为定向取材和目录提供基础 |
| 条款理解 | 关键词匹配，只做候选提示 | 模型为每块起一个小标签（付款、工期、违约……） | 同义表达不再漏掉 |
| 文件类型 | 不做判断，一律按合同审 | 看目录加开头判断类型，判不准交人工选择 | 一份管道服务多个业务 |
| 取材 | 每批携带全篇合同 | 只取相关块及前后相邻块 | 长合同可处理，单次提示下降一个量级 |
| 未命中处理 | 静默跳过 | 显式产出"未定位、待核实"并计入报告 | 漏查变成看得见 |
| 调用预算 | 全局 3 次 | 建索引 3 次 + 审查作答 3 次，分别记账 | 索引不挤占作答额度 |
| 模块边界 | 合同审查专用 | 公共管道 + 可替换的规则包 | 四个业务共用一套代码 |

## 3. 目标流程

```
1.  上传、校验、存库                 代码
2.  解析成带编号的段落               代码
3.  按"第X条"切块                   代码
4.  为每块打标签，并判断文件类型      模型   2–3 次调用
5.  按类型选规则包                   代码（映射表）
6.  按标签找相关块及前后相邻块        代码
7.  未命中的规则记为"未定位、待核实"   代码
8.  出题：目录 + 相关块 + 法条        代码
9.  逐条回答合不合规、依据是哪句       模型   最多 3 次
10. 校验引文、来源、字段              代码
11. 计算覆盖，判定成功/部分/失败       代码
12. 落库、页面展示、人工处理、复核、导出
```

模型只出现在第 4 步和第 9 步。其余由代码执行，且第 9 步的输出必须通过第 10 步校验才成为结论。

关键约束：

- 第 4 步的分类结果是**受限枚举**，不在枚举内即为无效输出；判为"不确定"时交人工选择，不向下推进。
- 第 6 步匹配不到任何块时，不允许沉默，必须产出待核实条目。
- 第 10 步不通过校验的条目进入 `rejected`，不进入结论。

## 4. 为什么不采用 agent 自主决定

### 4.1 三项能力会退步

**覆盖无法声明。** agent 加载哪些规则、读哪些段落，由模型当场决定。漏掉一类检查时，
系统不会报错，只会产出一份"看起来干净"的报告。现有实现中，少查一条规则会直接表现在
覆盖清单的"待核实"上。这是验收 AC-03、AC-21 的基础。

**结果不可复现。** 同一份合同两次运行可能走不同路径、得到不同结论。验收与答辩时无法
解释两次结果的差异，也无法回答"这条结论是怎么来的"。

**校验可以被绕过。** 现在的引文比对由代码强制执行，模型编造一句话就会被剔除。一旦模型
自行决定调用哪些工具，校验要么写进提示词（模型可能不遵守），要么做成一个工具（模型可以
不调用）。这条防线一旦交出去，前面所有工作都不成立。

此外，预算也随之不可控：现有契约是每次审查最多 3 次模型请求、单次 90 秒、总计 600 秒
（AC-23）。自主规划无法给出调用次数的上界。

### 4.2 规格已经明确排除

- `spec/01-product.md:299`：「使用固定业务流程，避免依赖开放式多智能体循环。」
- `spec/01-product.md:342`：「模型没有任意网址访问、命令执行、权限变更或写入已复核成果的工具权限。」
- `spec/00-overview.md:113`：「不引入 Redis、独立消息队列、向量数据库、Kubernetes 或通用智能体编排平台。」

值得说明的是，`spec/01-product.md:303` 已经写明「按条款标签、关键词和适用条件补充精选依据」，
即标签驱动取材是规格原本的要求，只是实现里没做全。本计划属于补齐既有契约，不是变更路线。

### 4.3 赛项要求与产品架构是两个层面

赛项任务要求「使用码道 CodeArts 代码智能体」「基于已有智能体和 Skills 开通 RDS、Redis 等
云服务」「基于智能体和 Skills 在华为云部署作品」。这三条约束的是**研发与交付过程**，
不是产品内部的推理方式。

因此「用智能体 + Skills」是必须完成的交付动作，与产品内部采用固定流程并不冲突。
两者混为一谈，会导致为了一个演示叙事而重写已经通过验证的校验逻辑。

### 4.4 什么情况下应当改变这个判断

- 赛项评分细则明确对"自主规划、多步推理"计分。当前规格已登记评分细则未独立核实。
- 产品目标从"四模块可验收的 Demo"变为"处理任意法律文档的助手"。后者需要检索层与知识库，
  知识来源从规则包换成检索结果，但控制流仍是"外层路由、内层固定管道"，不是自由循环。

### 4.5 可以采纳的部分

规则包的文件形态可以向 skill 靠拢：一份说明文档 + 规则数据 + 正反例，便于人工维护和模型阅读。
「加载了哪些规则」本身应作为结构化记录落库，正是上文的"未定位声明"。

**加载权仍留在代码**：必检规则强制加载，补充规则按标签加载。

## 6. 不做的事

- 自由多轮 agent 循环与通用编排平台。
- 向量数据库、独立队列、Redis。
- 由模型决定加载哪个规则包。
- 由模型直接修改合同正文。审查模块只产出修改建议；正文改写属于文书模块，
  且导出时不得重新润色用户已修改的内容（`spec/01-product.md:173`、§8.2）。
